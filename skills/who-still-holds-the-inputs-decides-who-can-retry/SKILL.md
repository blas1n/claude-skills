# 재시도를 누가 할 수 있는지는, 그때 입력을 누가 들고 있는지가 정한다

## Problem

- **증상**: 재전달 설계가 "얼마나 기다렸다가 다시 보낼까"(리스 시간, PEL idle,
  백오프)를 중심으로 짜인다. 옵션 비교표가 **타이밍 축으로만** 그려진다.
- **근본 원인**: 요청 페이로드의 일부는 **의도적으로 영속화되지 않는다.**
  - 요청 스코프 토큰(디스패치 시점에 민팅, 그 디스패치에만 유효)
  - 시크릿(env·헤더로만 전달 — 명령 문자열에 넣으면 DB·로그·스트림에 영원히 남는다)
  - 파생 컨텍스트(호출자 마감, 사용자 세션, 임시 워크스페이스 경로)

  백그라운드 스위퍼는 **DB 만 읽는다.** 그러니 이 필드들을 복원할 수 없고,
  복원하려면 *안 저장하기로 한 결정을 뒤집어야* 한다.
- **흔한 오해**: "행에 status 와 timestamp 가 있으니 스위퍼가 재구성할 수 있다."
  → 행에 있는 건 **영속화해도 되는 것들뿐**이다. 없는 것이 설계를 정한다.

## Solution

1. **재시도 후보를 고르기 전에 페이로드 빌더를 읽어라.** `if x:` 로 조건부로
   붙는 필드, 그리고 주석에 *"NOT persisted"* · *"ephemeral"* · *"belongs to this
   dispatch only"* 라고 적힌 필드를 세라. **그게 재시도 주체의 후보를 걸러낸다.**
2. **그 필드를 아직 메모리에 들고 있는 컴포넌트를 찾아라.** 대개 **요청을 보내고
   바로 결과를 기다리는 그 호출자**다. 보내는 줄과 기다리는 줄이 붙어 있으면
   재시도는 그 사이에 클로저 하나로 들어간다.
3. **재시도를 awaiter 의 콜백으로 만들어라** — 공유 함수는 *언제 다시 보낼지*만
   결정하고, *무엇을 보낼지*는 호출자가 준다.
4. **페이로드 빌더는 반드시 추출해 공유하라.** 최초 전송과 재전송이 각자 페이로드를
   만들면 갈라지고, 갈라진 쪽은 **드문 재시도 경로에서만** 드러난다.

```python
# 공유 함수는 "언제"만 안다
async def await_completion(..., redeliver: Callable[[float], Awaitable[None]] | None = None):
    ...
    if redeliver is not None and not settled and elapsed >= grace:
        settled = True                      # 한 번만 — 양방향으로
        if await _is_unreceived(task_id):   # 적극적으로 "못 받았다"가 확인될 때만
            await redeliver(deadline - now())   # 남은 마감을 넘긴다

# 호출자는 "무엇을"을 안다 — 방금 보낸 것을 아직 들고 있으니까
async def _redeliver(remaining_s: float) -> None:
    await redispatch_task(redis, task=task, worker_id=worker.id,
                          mcp=mcp, env=exec_env, timeout_s=remaining_s)
```

## Key Insights

- **"아직 안 받았다"를 적극적으로 기록해라.** 경과 시간으로 추론하면 *느린 실행*과
  *유실*을 영원히 구분 못 한다. 원자적 조건부 UPDATE 로 찍는 **수신 영수증**
  (`claimed_at`) 하나면 중복 방어가 **타이머가 아니라 WHERE 에서** 나오고, 한 시간
  도는 정상 턴이 구조적으로 안전해진다. 리스+하트비트는 이걸 근사할 수만 있다.
- **awaiter 가 죽으면 재시도가 없다 — 이건 결함이 아니라 옳은 동작이다.** 기다리는
  사람이 없는 작업을 되살리면 슬롯을 태워 허공에 보고한다. "스위퍼가 더 튼튼하다"는
  직관은 이 경우 **더 많이 하는 것을 더 낫다고 착각**한 것이다.
- **마감은 남은 것을 보내라.** 타임아웃이 "실행자가 시작한 시점부터"라면, 원래 값을
  다시 보내는 순간 재시도가 자기를 기다리던 호출자보다 오래 산다.
- **하위호환은 수신자의 능력으로 게이트해라.** 재시도를 못 거르는 구버전 수신자에게
  재전달하면 **두 번 실행**된다. 그리고 그 능력은 **등록 때 한 번 보낸 값으로 알 수
  없다** — 지금 도는 빌드를 말해주지 않는다. 매 요청 헤더로 announce 하게 하고,
  기본값은 *"모른다 = 재전달 안 함"* 으로 둬라(fail-closed = 오늘 동작 그대로).
- **바디가 아니라 헤더.** 요청 모델이 `extra="forbid"` 면 새 바디 필드는 **옛 서버가
  모든 요청을 422 로 거절**하게 만든다. 헤더는 모르는 쪽이 그냥 무시한다.
- **설계 보고서가 "옵션 A/B/C" 를 타이밍 축으로만 비교하고 있으면 축이 하나 빠진
  것이다** — *누가 입력을 들고 있나*. 그 축을 넣으면 후보가 대개 하나로 줄고,
  줄어든 쪽이 더 작고 더 안전하다.
