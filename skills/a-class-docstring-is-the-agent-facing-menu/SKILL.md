# 클래스 독스트링은 에이전트가 읽는 메뉴다

## Problem

- **증상**: 에이전트가 **존재하지 않는/폐기된** 파라미터를 계속 보낸다. 코드에는 그 키가
  없는데도 그렇다. 또는 툴 스키마에 한국어 개발자 메모·이슈 번호·TODO 가 섞여 나간다.
- **근본 원인**: pydantic(및 대부분의 스키마 → JSON Schema 변환기)은 **클래스 독스트링을
  `description` 으로 옮긴다.** MCP `tools/list` 는 그 JSON Schema 를 그대로 실어 보낸다.
  ⇒ 개발자에게 쓴 산문이 **모델의 프롬프트가 된다.**
- **흔한 오해**: "독스트링은 사람용, 설명은 `description=` 파라미터용" — 아니다. 클래스
  독스트링에 `description` 을 따로 안 주면 **독스트링이 곧 그것**이다. 그리고 `Field(...)`
  의 독스트링/주석도 필드 설명으로 올라간다.

특히 고약한 형태: **폐기된 키를 설명하는 문장이 폐기된 키를 메뉴에 다시 올린다.**
*"`enabled` 는 더 이상 받지 않는다"* 라고 적으면, 모델이 보는 텍스트에는 `enabled` 가 있다.
모델은 부정문보다 **이름의 존재**에 반응한다.

## Solution

1. 스키마 클래스의 **독스트링은 지금 계약만** 적는다 — 필드가 무엇이고 무엇이 허용되는지.
   한두 문단, 기계가 읽어도 되는 말만.
2. **내력·이유·경고는 모듈 독스트링이나 `#` 주석으로.** 주석은 어떤 변환기에도 안 실린다.
   (모듈 독스트링도 안 실린다 — 클래스/필드 단위만 올라간다.)
3. 가드를 **와이어에서** 건다. 소스를 grep 하지 말고 실제로 직렬화된 것을 읽어라:

```python
def test_no_tool_advertises_the_dead_key() -> None:
    registry = build_registry()
    wire = {t.name: t for t in registry.list_tools()}   # 실제 tools/list 산출물
    # 대상 집합은 레지스트리에서 센다 — 하드코딩 목록은 내가 본 툴만 증명한다
    targets = [t for t in tools_with_field("trigger")]
    for t in targets:
        blob = f"{wire[t.name].description}\n{wire[t.name].inputSchema}"
        assert "enabled" not in blob
```

4. 범위를 좁혀라 — 같은 레지스트리에 `set_enabled` 처럼 **정당한** 동음이의가 있다.
   대상은 "그 필드를 들고 있는 툴"로 런타임에서 고른다.

## Key Insights

- **이 가드는 자기 자신에게도 걸린다.** 제거 내력을 클래스 독스트링에 적는 순간 방금 만든
  가드가 빨개진다 — 그게 정상이고, 그 빨강이 곧 증거다. 가드를 느슨하게 만들지 말고
  문장을 주석으로 내려라.
- 배포본에서 한 번 **실제로 읽어 봐라**. 로컬에서 지웠다고 생각한 문장이 이미 배포된
  스키마에 실려 있을 수 있다(`docker exec … list_tools()`).
- 일반화: **개발자용 표면과 기계용 표면이 같은 문자열을 공유하는 자리**를 찾아라 —
  독스트링, `help=`, i18n 키, 에러 메시지. 거기 적은 산문은 **검증 대상 주장**이다.
- 짝이 되는 결함: 스키마가 그 키를 **받아 주면**(untyped dict) 메뉴를 믿은 에이전트가
  실제로 써 넣는다. **설명과 스키마는 한 문의 두 짝**이라 같이 닫아야 한다.
