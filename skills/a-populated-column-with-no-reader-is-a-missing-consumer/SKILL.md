# 채워져 있는데 아무도 안 읽는 칸 — 없는 건 슬롯이 아니라 독자다

## Problem

기능 요청("제품마다 다른 방으로 보내고 싶다")을 코드로 재면 이런 결론이 나온다:

> 목적지는 **부모(계정)** 설정에만 있다 ⇒ 자식(바인딩)마다 다르게 하려면 **새 키가 필요하다.**

그리고 그 결론은 **코드만 읽으면 반증되지 않는다.** 코드에는 정말로 독자가 없기 때문이다.

- **증상**: 설계가 "새 컬럼 + 마이그레이션 + UI 노출" 로 커진다. 기존 사용자에게는
  마이그레이션/백필 얘기가 붙는다.
- **근본 원인**: 슬롯은 **이미 있었고 이미 채워져 있었다.** 없는 것은 **소비자**다.
  누군가(사용자·부트스트랩·예전 UI)가 그 칸에 써 왔는데, 읽는 코드가 한 줄도 없어서
  **grep 으로는 "안 쓰인다"** 로 보인다.
- **흔한 오해**: *"코드에 독자가 없다 = 그 슬롯은 이 용도가 아니다."*
  실제로는 *"독자가 없다 = 아무도 배선을 안 했다"* 인 경우가 많다. 특히 자유형 JSON
  컬럼은 **쓰는 쪽이 읽는 쪽보다 먼저 생긴다.**

## Solution

새 키/컬럼을 제안하기 **전에** 세 가지를 순서대로 한다.

1. **prod 행을 조회한다.** 코드가 아니라 **데이터**다. 넣으려는 값이 이미 어딘가에
   적혀 있는가?

   ```
   # 예: 바인딩과 계정을 나란히 덤프
   bindings_list()   -> selection
   connectors_list() -> delivery_config
   ```

2. **중복을 센다.** 같은 값이 몇 군데 있나? 중복 자체가 센서다.

   | 층 | 값 |
   |---|---|
   | `resource_id` | `"8242700007"` |
   | `binding.selection.chat_id` | `"8242700007"` |
   | `account.delivery_config.chat_id` | `"8242700007"` |

   세 벌이면 **새 키는 네 번째 사본**이다. 그리고 기존 세 벌 중 하나는 이미
   "그 의도로 쓰인" 칸이다.

3. **읽게 만드는 비용과 새로 만드는 비용을 나란히 적는다.** 보통 이렇게 갈린다.

   | | 있는 걸 읽는다 | 새 키를 만든다 |
   |---|---|---|
   | 마이그레이션 | 0 | 1 + fresh-PG 스모크 |
   | 기존 데이터 | **즉시 의미를 갖는다** | **영원히 고아** |
   | 오늘의 동작 변화 | prod 값이 부모와 같으면 **증명 가능한 no-op** | 동일 |
   | 계약 | 그 칸의 의미가 넓어진다(문서화 필요) | 깔끔하게 분리 |

4. **no-op 이라는 사실을 테스트로 박는다.** "오늘 prod 행은 전부 부모와 값이 같으니
   켜도 아무것도 안 움직인다" 는 **안전 논거의 전부**다. PR 설명이 아니라
   **거짓이 되면 빨개지는 곳**에 있어야 한다.

   ```python
   def test_todays_prod_shape_is_a_no_op():
       same = {"chat_id": "8242700007"}
       assert effective_config(binding(selection=same, parent=same)) == same
   ```

5. **소비자를 배선할 때 소비 지점을 센다.** 한 값을 읽는 곳이 둘 이상이면(이벤트
   빌더 + 플러그인 컨텍스트 등) **한 이름을 계산해 둘이 같이 읽게** 하고,
   **각각 따로 절단해 테스트가 하나씩 뒤집히는지** 확인하라. 한쪽만 병합하면
   "이벤트는 새 목적지, 실행은 옛 설정" 인 반쪽 배선이 된다.

## Key Insights

- **grep 은 "독자 없음"을 증명하지 "무용함"을 증명하지 않는다.** 자유형 JSON 칸에서는
  생산자가 소비자보다 먼저 생기는 게 정상이다. `[[a-dead-entity-can-be-the-subject-of-a-live-claim]]`
  의 **정확한 반대편**이다 — 그쪽은 *생산자 없는데 주장은 살아 있는* 경우, 이쪽은
  *데이터는 살아 있는데 읽는 코드가 없는* 경우.
- **같은 값의 사본 개수가 첫 센서다.** 세 벌이 보이면 이미 누군가 "여기에 적으면
  되겠지" 를 한 것이다. 네 번째를 만들지 마라.
- **선택지를 낼 거면 대가부터 재라.** "마이그레이션 1건" 같은 대가는 **주장**이고,
  사용자는 그 숫자로 결정한다. 틀린 대가로 고른 선택은 되돌리는 데 두 번의 질문이 든다
  (`[[confirm-the-premise-before-offering-the-choice]]`).
- **기존 슬롯을 읽게 하면 계약이 넓어진다** — 그건 대가지 결함이 아니다. 다만
  **문서에 적어야** 한다: 그 칸을 읽는 다른 소비자(예: 인바운드 라우팅 힌트)가
  이미 있다면, 이제 한 dict 가 두 방향을 섬긴다는 사실이 어딘가에 적혀 있어야 한다.
- **유니크 제약을 확인하라.** 자식 행이 한 부모에 여럿일 수 있으면 "어느 값이 이기나"가
  생긴다. 바깥으로 나가는 동작(배송·알림)이면 **추측하지 말고 오버라이드를 버려라** —
  행 순서에 목적지가 좌우되는 것보다 부모 기본값이 낫다. 값이 같은 중복은 모호함이
  아니므로 그 대조군도 같이 테스트하라.
