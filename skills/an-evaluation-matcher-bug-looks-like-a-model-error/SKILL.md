# 채점기 짝짓기 버그는 모델 오류처럼 보인다

## Problem

hots-replay-analysis PR #23에서 리플레이 선택 식별 규칙을 독립 라벨 101구간과 대조했다. 첫 채점에서는 새 규칙(v3)의 개발용 정밀도가 0.50으로 시제품(0.68~0.80)보다 나빴다. FP를 한 건씩 열어 보니 상당수가 규칙 오류가 아니었다.

- **허용 오차가 옆 구간을 먼저 잡음:** `start-1 ≤ t ≤ end+1`로 순서대로 찾았다. 그래서 자동 시점 120.81이 검토자의 전략적 구간(120.81–121.62)이 아니라 바로 앞 무빙 구간(118.88–120.06)에 붙었다. 결과는 FP였다.
- **반올림:** 자동 시점 694.1875인데 라벨 시작은 694.19로 0.01초 단위였다. 정확 포함이 실패하고 앞 구간으로 넘어갔다.
- **이름 대응표 누락:** v3의 새 출력(`take_camp`, `relocate`, `rotate_to_lane_N`)이 대응표에 없었다. 모두 종류 불일치로 셌다.
- 흔한 오해: 채점기는 단순해서 맞을 것이라 여기고, 숫자가 나쁘면 규칙을 바꾼다.

## Solution

1. **임계값을 바꾸기 전에 FP·종류 불일치를 한 건씩 출력한다.** 판정, 자동 시점, 짝지어진 라벨 구간을 함께 본다. 자동 시점이 다른 전략적 구간 안에 있는데 FP로 나왔다면 채점기 버그다.
2. **짝짓기는 정확 포함을 먼저 하고, 라벨 정밀도만큼 여유를 준다.** 0.01초 반올림이면 ±0.05를 둔다. 허용 오차 짝짓기는 그 다음이다.
3. **새 규칙 버전이 출력 이름을 추가하면 대응표부터 갱신한다.** 대응표에 없는 이름은 조용히 오답으로 세지 말고 오류로 드러나게 한다.
4. **채점기를 고치면 기준선(이전 규칙)도 같은 채점기로 다시 잰다.** 비교가 공정해진다. 고친 내용은 보고서에 적는다.
5. **튜닝은 개발용만으로 한다.** 보류용은 규칙을 고정한 뒤 한 번만 채점하고, 그 결과로 다시 고치지 않는다. 채점기 수정은 규칙 튜닝이 아니므로 고정 전에 끝낸다.

## Key Insights

- 시점 탐지 대 구간 라벨의 짝짓기에서는 **구간 경계 바로 근처의 정답**이 가장 흔하다. 결정은 대개 새 구간의 첫 클릭이기 때문이다. 그래서 허용 오차 순서 버그가 가장 중요한 사례에 집중해서 터진다.
- 시제품과 실제 코드의 점수가 다르면, 둘이 같은 채점기 버전을 썼는지부터 확인한다.

## Red Flags

- FP 사례에서 자동 시점과 라벨 구간 시작이 0.1초 안쪽으로 붙어 있다.
- 새 규칙에서 "종류 불일치"가 갑자기 늘었고, 그 규칙이 출력 이름을 바꿨거나 추가했다.
- 숫자를 보자마자 임계값 스윕을 시작하려 한다.

사례 추가 (2026-10-23, hots PR #30 보완): 오탐 규칙("지점 37.5 안 이동 클릭 = 오브젝트 활동")을 걷어내자 기계 의미 판정 exact가 42→30으로 떨어졌다.
잃은 13건 중 12건이 그 규칙의 후보였다. 그런데 기계 판정(`gt.command_meaning`)도 지점 근처 이동을 objective로 읽는 **같은 편향**이었다 —
걷어낸 규칙과 판정기가 같은 방향으로 기울어 서로를 "정답"으로 확인하고 있었다. 규칙을 고친 뒤 자동 지표가 나빠지면, 판정기가 고친 규칙과
같은 가정을 공유하는지부터 확인하고, 그 경우 감소를 퇴보로 보고하지 마라(블라인드 사람/독립 검토로 재라).
