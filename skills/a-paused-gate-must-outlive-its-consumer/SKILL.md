# 잠깐 내린 게이트는 그것을 읽는 소비자보다 오래 내려가 있어야 한다

## Problem

bsvibe-app 에서는 PR 을 열거나 머지하거나 PR 에 푸시하면 prod 런이 열린다. 기록용 PR 은 이렇게 다뤘다:

```
바인딩 필터 일시정지 → PR 열기 → runs_list 에 새 런 없음 확인 → 필터 복원
```

여덟 번 잘 됐다. 아홉 번째(#1130)에 런이 열렸다 — 3.2만 토큰, 형님께 질문 알림.

```
04:22:09.9  webhook_received            ← 필터는 아직 일시정지
04:22:13.5  필터 복원 {}                 ← "runs_list 비었음" 확인 직후
04:22:14.4  런 f26ef907 생성             ← intake 워커가 이제야 이벤트를 처리, 복원된 필터로 판정
```

**필터는 웹훅을 받을 때가 아니라 intake 워커가 저장된 이벤트를 처리할 때 적용된다.** 앞의 여덟 번은
intake 가 우연히 복원 전에 돌았을 뿐이다.

### 왜 잘 속나

* **확인이 초록이었다.** 동작 직후의 `runs_list` 는 런이 없다 — 아직 만들어지지 않았기 때문이다. 이 확인은
  빨개질 수 없는 시점에 돌았다(`a-check-that-cannot-flip-is-not-measuring-anything` 의 시간 축 버전)
* **반복 성공이 절차를 굳혔다.** 여덟 번의 성공은 절차의 증거가 아니라 intake 주기와 내 복원 속도의 우연이었다
* **"웹훅 → 필터"라는 그림이 자연스럽다.** 실제 경로는 웹훅 → 저장 → (나중에) 소비자가 필터를 읽고 판정

## Solution

### 1. 게이트를 누가, 언제 읽는지부터 찾는다

게이트 값이 쓰이는 코드를 grep 해서 **읽는 쪽**이 동기 수신기인지 비동기 소비자인지 본다. 비동기면 복원 시점이 그 소비자의
처리 시점에 묶인다.

### 2. 센서는 소비자의 판정이다 — 결과의 부재가 아니다

```bash
# bsvibe: intake 가 이 이벤트를 '필터로 거절'했다는 소비자 자신의 기록
docker --context colima logs --since 3m bsvibe-prod-worker-1 | grep filter_rejected
# → {"event": "intake_worker_trigger_fi…", "reason": "filter_rejected", "trigger_event_id": …}
```

그 줄을 본 **뒤에** 복원한다. 로그를 볼 수 없으면 소비자 주기보다 넉넉히(여기선 ≥60초) 기다린다. "결과 없음" 확인은
판정 로그를 본 뒤의 보조일 뿐이다.

### 3. 새어 나갔으면 즉시 되돌리고 알린다

열린 런은 바로 취소한다(여기선 #1106 이후 취소가 세션을 4초 안에 멈춘다). 그 런이 사람에게 알림을 보냈을 수 있으니
사용자에게 그대로 말한다.

### 4. 절차 문서를 고친다

이 사고의 원인은 인수인계에 적힌 "열고 바로 복원"이었다. 절차가 문서에 있으면 문서를 고치는 것이 수정이다.

## Key Insights

- **게이트의 수명은 그것을 읽는 쪽이 정한다.** 쓰는 쪽(나)의 동작이 끝난 시점이 아니라, 읽는 쪽(소비자)이 그 이벤트를
  판정한 시점까지 내려가 있어야 한다.
- **"동작 직후 결과 없음"은 측정이 아니다.** 결과가 비동기로 생기면 그 확인은 언제나 초록이다. 소비자의 판정 로그처럼
  **반대 판정도 낼 수 있는** 신호를 봐라.
- **반복 성공은 타이밍 우연을 숨긴다.** N 번 성공한 절차도 경로에 큐가 있으면 의심하라 — 실패는 소비자가 한 번 늦을 때 온다.
