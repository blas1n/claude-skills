# 가드가 자기 설명에 걸리면 느슨해진다

## Problem

- **증상**: 부재 가드를 새로 만들었는데 **바로 빨개진다.** 열어 보면 위반은
  프로덕션 코드가 아니라 *"이건 2026-09-11 에 제거됐다"* 라고 적은 **내 주석·독스트링**이다.
- **근본 원인**: 폐기를 설명하려면 **폐기된 이름을 써야 한다.** 그래서 가드를
  만드는 행위 자체가 위반을 생산한다.
- **왜 위험한가**: 빨강이 결함을 뜻하지 않으면 사람은 **가드를 고친다** — 철자를
  빼거나, 파일을 목록에서 지우거나, 검사를 지운다. 그 순간 가드는 진짜 재발을
  못 잡는다. **가드가 죽는 경로는 삭제가 아니라 완화다.**

2026-09-23 하루에 **네 번** 같은 모양이 났다:
1. `trigger.enabled` 부재 가드 ← 모델 독스트링의 제거 내력
2. MCP 와이어 설명 가드 ← pydantic 클래스 독스트링에 적은 내력(이건 **진짜 결함**이기도 했다)
3. logrotate 하드코딩 금지 가드 ← *"예전엔 이 패턴이었다"* 주석
4. `is_open` 부재 가드 ← 그 게이트가 왜 사라졌는지 적은 함수 독스트링

## Solution

**명제를 좁혀라 — "이 파일에 그 글자가 없다"가 아니라 "코드가 그것을 읽지 않는다".**

1. **주석/독스트링을 걷어내고 검사한다.**

```python
def _code_only(text: str) -> str:
    text = re.sub(r'"""(?:.|\n)*?"""', "", text)      # 파이썬 독스트링
    text = re.sub(r"/\*(?:.|\n)*?\*/", "", text)      # 블록 주석
    text = re.sub(r"^[ \t]*(?:#|//).*$", "", text, flags=re.MULTILINE)
    return text
```

```bash
code=$(grep -vE '^[[:space:]]*#' "$SCRIPT")   # 셸이면 이 한 줄로 족하다
```

2. **함수 단위로 좁히는 게 더 낫다.** 파일이 아니라 `inspect.getsource(fn)` 을 보고,
   거기서 독스트링을 뺀다. 명제가 *"이 규칙이 그 필드를 읽지 않는다"* 로 정확해진다.

3. **스트리퍼에 양방향 대조군을 붙여라.** 스트리퍼가 파일을 통째로 삼키면
   가드는 영원히 초록이다. 그건 완화보다 더 조용한 죽음이다.

```python
assert "authorized_user_ids" in code, "스트리퍼가 코드를 먹었다"
```

4. **단어 경계를 쓴다.** `enabled:` 는 무관한 `quiet_hours_enabled:` 를 잡는다.
   `\benabled\s*:` 로 좁혀라 — 틀린 이유로 빨개지는 것이 완화의 첫 단추다.

## Key Insights

- **가드의 실패 모드는 두 개다**: 못 잡는 것(거짓 음성)과 **틀린 이유로 잡는 것**
  (거짓 양성). 후자가 더 위험하다 — 사람이 가드를 직접 약화시키게 만들기 때문이다.
- **제거 내력은 지우지 마라.** 왜 사라졌는지는 결론보다 오래 쓸모 있다.
  내력을 없애는 게 아니라 **검사 범위를 좁히는 것**이 답이다.
- ⚠️ **예외 하나**: 그 산문이 **기계가 읽는 표면**이면 그건 진짜 결함이다 —
  pydantic 클래스 독스트링은 MCP 와이어 스키마가 된다.
  → [[a-class-docstring-is-the-agent-facing-menu]]
  그때는 문장을 주석이나 모듈 독스트링으로 **옮겨라**(주석은 어디에도 안 실린다).
- 같은 함정에 두 번 걸리면 스트리퍼를 **공용 헬퍼로** 빼라. 네 번 걸린 뒤에야
  이걸 적었다 — 반복 횟수 자체가 신호였다.
