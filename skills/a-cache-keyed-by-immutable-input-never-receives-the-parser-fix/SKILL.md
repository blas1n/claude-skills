# 불변 입력으로만 키잉된 캐시는 **파서 수정을 영원히 못 받는다**

## Problem

비싼 파생값을 디스크에 캐시한다. 원본은 **진짜로** 불변이다 — 제출된 SEC 파일링,
git blob, 릴리스된 아티팩트, 업로드 완료된 이미지. 그래서 이 코드가 옳아 보인다:

```python
cache = root / "risk_factors" / f"{cik}_{accession}.txt"
if cache.exists():
    return cache.read_text()      # 파일링은 절대 안 바뀐다 → 무효화 불필요
text = extract_item_1a(html)       # ← 이 함수를 오늘 고쳤다
cache.write_text(text)
```

캐싱 판단은 맞다. **틀린 건 키다.** 키는 입력만 담고 있고, 저장된 값은
`extract_item_1a` **버전의 함수**다.

- **증상**: 없다. PR 머지, CI 초록, 배포 성공, 유닛 테스트 통과(테스트는 자기 픽스처
  HTML 을 파싱하므로 **캐시를 안 거친다**). 프로덕션은 옛 출력을 계속 쓴다.
  실측: 디스크의 약 7,000건 **전부** 수정 전 출력이었고, 수정은 **0건**에 도달했다.
- **근본 원인**: 캐시 키가 **변한 차원(파생자 버전)을 빼고** 있다. 입력이 불변일수록
  캐시 히트율이 100% 에 가까워지므로, **불변성이 강할수록 수정이 덜 도달한다.**
- **흔한 오해**: *"배포했으니 다음 실행부터 새 로직이 돈다."* 새 로직은 돈다 —
  **캐시 미스일 때만.** 그리고 미스는 신규 원본에서만 난다.

### 섞인 캐시가 균일하게 낡은 캐시보다 나쁘다

신규 항목은 새 파서로, 기존 항목은 옛 파서로 들어온다. 그러면 시스템이
**점점 올바르게 보이면서** 역사적 대량 데이터는 계속 틀려 있다. 그 대량 데이터가
백테스트·랭킹·집계의 입력이면, 측정값은 **두 파서 버전의 혼합**이 되고
전/후 비교가 성립하지 않는다.

## Solution

1. **캐시 키에 파생자 버전을 넣는다.** 디렉터리 한 겹이면 충분하고, 옛 디렉터리를
   남겨 두면 롤백이 공짜다.

```python
ITEM_1A_PARSER_VERSION = "v2"   # extract_item_1a 의 반환이 달라질 때마다 올린다

cache = root / "risk_factors" / ITEM_1A_PARSER_VERSION / f"{cik}_{accession}.txt"
```

2. **버전을 올리는 조건을 주석으로 못 박는다** — "로직을 바꿀 때"가 아니라
   **"반환값이 달라질 때"**. 리팩터링은 올리지 않고, 경계 조건 하나만 바꿨어도 올린다.
3. **재생성 비용과 착지 시점을 미리 재라.** 실측 ~1건/s · 약 7,000건 → 약 1시간이었고,
   크론이 장 개장까지 13.5시간 여유라 그냥 한 번 다시 받게 뒀다. 여유가 없으면
   사전 워밍을 하되, **공유 캐시에 쓰는 행위**임을 인지하고 소유자 판단을 받아라.
4. **스키마 버전과 혼동하지 마라.** 컬럼/필드 모양이 안 바뀌었으면 feature 스키마
   버전은 올릴 게 아니다. 바뀐 건 **값**이고, 값의 출처는 파서다.

## Key Insights

- **"입력이 불변"은 캐시 무효화가 불필요하다는 근거가 못 된다.** 캐시된 건 입력이 아니라
  **입력에 코드를 적용한 결과**다. 키는 그 둘을 **모두** 담아야 한다.
- **테스트는 이 결함을 구조적으로 못 잡는다.** 파서 테스트는 픽스처를 직접 파싱하므로
  항상 새 코드를 지난다. 캐시를 지나는 경로를 따로 테스트하지 않으면 영원히 초록이다.
- **센서는 배포가 아니라 저장소다.** "코드가 prod 에 있다"가 아니라
  **"새 버전으로 생성된 행 / 전체"** 를 세라. 0/7000 이면 수정은 존재하지 않는 것과 같다.
  → [[green-does-not-prove-deployed-measure-the-row]]
- **같은 가족의 함정이다**: 캐시 키가 실제로 변하는 차원보다 **거칠 때** 생긴다.
  per-run 토큰을 디렉터리 단위로 캐시하면 첫 토큰을 계속 쓰고
  ([[a-cached-config-layer-keeps-the-first-credential-it-saw]]), 파생 텍스트를 입력
  단위로 캐시하면 첫 파서를 계속 쓴다. **"무엇이 변하는가"를 적고 키와 대조하라.**
- **파생값이 랭킹·검증의 입력이면 수정 자체보다 재측정이 더 중요하다.** 수정이 캐시에
  도달한 뒤의 숫자만이 유효하다 — 그 전 숫자는 옛 파서의 것이다.

## Red Flags

- `if cache.exists(): return read()` 가 **파생값** 위에 있고, 키에 버전이 없다.
- 주석/인수인계에 "원본은 불변이라 무효화가 필요 없다"가 적혀 있다.
- 파서·추출기·정규화를 고쳤는데 **프로덕션 지표가 전혀 안 움직인다**(혹은 신규 항목에서만
  움직인다).
- 캐시 디렉터리의 mtime 이 대부분 **몇 달 전 한 시점**에 몰려 있다.
- 백테스트와 라이브가 같은 파생 캐시를 공유한다(수정이 한쪽에만 도달할 수 있다).
- "테스트는 통과하는데 실제로 바뀌었는지 확인할 방법이 없네"라고 생각한 순간.
