# 「가장 긴 구간」은 모호성 해소가 아니라 **병리적 후보 선택기**다

## Problem

반구조 문서에서 한 절만 떼어내야 한다. 시작·종료 패턴은 명확해 보인다.

```python
_START = re.compile(r"(?i)item\s*1a\b")
_END   = re.compile(r"(?i)item\s*1b\b|item\s*2\.")
```

문제는 시작 패턴이 **문서 안에서 여러 번 걸린다**: 목차 항목, 본문 상호참조,
페이지마다 반복되는 러닝 헤더. 그래서 모호성을 푸는 규칙이 필요하고, 가장 자연스러운
선택이 이것이다 — 실제로 코드에 이렇게 **의도적으로** 적혀 있었다:

> `# 가장 긴 구간을 고른다. 목차와 상호참조는 짧으니 이 휴리스틱이 그것들을 피해 간다.`

그럴듯하다. 그리고 **정확히 거꾸로다.**

- **증상**: 없다. 추출은 성공하고, 길고 그럴듯한 산문이 나온다. 예외도 빈 값도 없다.
  다운스트림(TF 코사인, 임베딩, 요약)은 아무 불만 없이 그걸 랭킹에 쓴다.
- **근본 원인**: 엉뚱한 시작점은 **종결자가 멀다**. 문서 앞쪽 주의문구에 박힌
  상호참조("…자세한 내용은 **Item 1A** 위험요인 참조…")에서 시작하면, 그 뒤 첫 종결자는
  한참 아래에 있다. 따라서 그 구간이 **항상 가장 길다.** 올바른 헤딩에서 시작한
  제대로 닫힌 구간은 언제나 더 짧으므로 **구조적으로 진다.**
  실측: 검사한 문서 **5건 전부** 주의문구에서 시작해 사업 설명과 임원 프로필까지 삼켰다.
- **흔한 오해**: *"극값으로 고르면 쓰레기 후보가 걸러진다."* 쓰레기 후보는 짧은 게 아니다.
  **경계를 모르는 후보라서 길다.**

### 종결자 쪽에도 같은 버그가 거울처럼 있다

시작만 고치는 건 절반이다(첫 시도가 측정으로 뒤집힌 지점). 종결자도 본문 문장에 걸린다 —
"see Part I, **Item 2.** Management's Discussion" 한 줄 때문에 구간이 738자에서 끊기고,
어떤 종목은 **5년 내내 780자 조각**으로 랭킹되고 있었다.

## Solution

**유효성을 극값이 아니라 술어(predicate)로 만들어라.** 극값은 이미 유효한 후보들 사이의
타이브레이크로만 남긴다.

1. **구조에 앵커링한다, 문자열이 아니라.** 블록 레벨 태그 경계를 줄바꿈으로 바꾼 텍스트를
   만들고, 시작은 **줄 머리**에 있어야만 인정한다(앞에 허용되는 건 페이지 라벨·"PART I"·
   "Table of Contents" 같은 헤딩 노이즈뿐). 문장 중간 상호참조는 이제 앵커가 못 된다.
2. **종결자도 같은 기준으로 앵커링한다.** 단, 종결자를 자기 줄에 두지 않는 작성자가 있으니
   **헤딩 종결자가 없을 때만** 아무 데나 나오는 첫 등장으로 폴백한다.
3. **밖에 있어야 할 절을 품은 후보를 탈락시킨다.** 구간 안에 `Item 1 … Business` 헤딩이
   있으면 그 구간은 사업 설명 앞에서 열린 것이다 → 버린다. 이것이 목차 항목도 같이 잡는다.
4. **생존자들 사이에서만 가장 긴 것을 고른다.** 길이는 이제 "선택 이유"가 아니라
   동률 처리용이다(본문 중간에 반복되는 러닝 헤더가 더 짧은 후보를 만든다).
5. **기존에 올바르게 읽히던 문서는 바이트 단위로 같아야 한다.** 블록 텍스트를 공백
   정규화하면 옛 경로의 입력과 동일함을 테스트로 고정하라 — 그래야 수정이 회귀가 아니다.

```python
# 극값으로 고르기 (틀림) — 엉뚱한 시작점이 항상 이긴다
best = max(candidates, key=lambda c: c.end - c.start)

# 술어로 걸러낸 뒤에만 극값 (맞음)
valid = [c for c in candidates
         if starts_at_line_head(c) and not contains_outside_section(c)]
best = max(valid, key=length) if valid else None
```

## Key Insights

- **극값은 "정상 범위의 대표"가 아니라 "가장 극단적인 사례"다.** 모호성 해소에 극값을 쓰면
  고르는 건 평균적 후보가 아니라 **가장 망가진 후보**다. 이건 longest 뿐 아니라
  first/last/max 전부에 해당한다 — "왜 이 극값이 올바름과 상관되는가"를 말로 설명할 수
  없으면 그건 모호성 해소 규칙이 아니다.
- **출력이 비어 있지 않다는 건 아무 증거도 아니다.** 추출기·파서의 실패 모드는 대개
  "실패"가 아니라 **"다른 것을 성공적으로 추출"** 이다. 길이가 늘면 더 성공처럼 보인다.
- **센서는 비교 가능한 입력들 사이의 크기 분포다.** 같은 회사 인접 연도인데 94,948자 →
  176,872자(≈2배)가 떡하니 있었고, 전체 최악은 **548배**였다. 수정 후 인접 비율
  p99 2.64→1.64, 최대 548x→5.1x. 이 분포는 콘텐츠를 안 읽고도 뽑을 수 있다 — 추출기를
  고치기 전에 **먼저 재야 할 숫자**다.
- **성질 기반 테스트가 예시 테스트보다 강하다.** "이 문서에서 이 문장이 나온다"는
  망가진 구간에서도 통과한다. "구간 안에 임원 테이블이 없다 / Item 1 Business 헤딩이
  없다 / 헤딩에서 시작한다"는 망가진 구간을 잡는다.
- **랭킹 신호로 쓰이고 있었다면 범위가 더 넓다.** 추출된 텍스트가 전략의 점수가 되고 있으면,
  이 버그는 "파서 버그"가 아니라 **"설계 문서가 말하는 것과 다른 것을 재고 있었다"** 다.
  고친 뒤 **검증 지표(백테스트·게이트)를 반드시 재돌려라** — 통과 근거가 그 위에 있었다.

## Red Flags

- 코드 주석이 극값 선택을 **정당화**하고 있다("긴 걸 고르면 짧은 노이즈를 피한다").
- 같은 종류의 입력인데 추출 길이가 2배 이상 흔들린다. 또는 어떤 항목이 수년간
  의심스럽게 짧다(780자).
- 추출 결과에 **있을 수 없는 어휘**가 보인다(위험요인인데 `Chief Executive Officer`,
  `vice president` 가 수십 번).
- 시작 패턴이 목차·상호참조·러닝 헤더에도 걸리는 걸 알면서 **경계 조건 없이** 매칭한다.
- "추출은 되는데 하위 지표가 좀 이상하다"로 넘어간 적이 있다.
- 종결자가 본문 문장에 등장할 수 있는 흔한 문자열이다(`Item 2.`, `Section 3`, `END`).
