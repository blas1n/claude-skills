# 브라우저의 자동 보정에 기대는 E2E 는 느린 CI 에서 흔들린다

## Problem
hpgg: 데이터만 바꾼 PR(#101) CI 에서 "영웅 상세 #builds-title 링크로 열면 그 섹션에 착지" E2E 가 5 s 폴링 타임아웃. 로컬 단독 12/12, 병렬 부하 40/40 통과 — 재현 불가.
- 측정(Playwright + CDP): 기본 페이지에서 300 ms 에 오프셋 539 px → 1.5 s 에 6 px. 즉 **처음 착지는 틀리고, 누군가 나중에 바로잡는다.**
- 가설 기각을 숫자로: 폰트 woff2 2 s 지연 → 정상(5 px), 이미지 6 s 지연 → load 전 이미 정상, CPU ×8 → 1.5 s 에 정상. 폰트·이미지·load 이벤트가 원인 아님.
- 코드 확인: 앱이 해시로 재스크롤하는 건 `?mode=sl` 같은 파라미터가 있을 때뿐(그 경우 섹션이 hydration 후 바뀌니까). 기본 링크는 **브라우저의 자체 보정**에 의존 → 하이드레이션이 느린 러너에선 5 s 안에 안 올 수 있음. 직전 PR(#98)이 착지 대상 위쪽 내용을 늘려 첫 착지 오차가 커진 것이 노출 계기로 추정.

## Solution
1. 실패 단언이 기다리는 "최종 상태"를 **누가 언제 만드는지** 시간축으로 측정(100 ms 간격 폴링으로 착지 시점 기록).
2. 의심 요인을 하나씩 격리해 지연시키고(route 지연, CDP CPU throttle) 결과가 바뀌는지 본다 — 안 바뀌면 기각하고 적는다.
3. 제품: 보정을 앱이 직접, 결정적으로(hydration 직후 rAF + `document.fonts.ready` 후 한 번 더), 사용자가 스크롤했으면 하지 않게.
4. 테스트: 조건은 그대로, 대기 시간만 늘리고 **이유를 주석으로**(느린 러너의 hydration).
5. PR 설명에 "로컬 재현 실패, 기각한 가설, 방어적 변경"을 그대로 쓴다. 증명 못 한 개선을 주장하지 않는다.

## Key Insights
- "결국 맞아진다"는 단언은 그 "결국"의 주인이 내 코드가 아닐 때 러너 속도에 종속된다.
- 재현이 안 될 때 할 수 있는 정직한 일: 메커니즘을 측정하고, 의존을 제거하고, 남은 불확실성을 문서화.
- 데이터 PR 에서 UI 테스트가 깨지면 직전 UI PR 의 레이아웃 변화를 먼저 의심.

## Red Flags
- `expect.poll(...)` 기본 5 s + 스크롤/레이아웃 단언
- 앱 코드에 해당 보정 로직이 조건부로만 존재
- "로컬에선 통과" 로 재실행해 넘기기
