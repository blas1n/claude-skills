# claim 을 반납해도 그 claim 으로 띄운 일은 멈추지 않는다

## Problem

"재시작하면 돌던 작업을 바로 큐로 돌려놓는다"를 구현하고 운영에서 확인하려고 실행 중에
워커를 재시작했다.

```
08:34:57  worker   stop() → 작업 취소 → running → open        ← 반납 OK
08:35:00  worker'  (새 프로세스) claimed_for_drive             ← "1초 만에 재claim" — 여기서 성공이라고 보고했다
08:35:01  backend  mcp_work_tool file_edit run=…               ← 옛 실행 턴이 아직 편집 중
08:35:01  backend  sandbox_removed → sandbox_created (sbx-<run>)
08:35:02  worker'  sandbox create: container name … already in use → run FAILED
```

- 워커 안의 태스크는 취소됐지만, 그 태스크가 **원격 실행기에 넘긴 턴**은 워커 밖에서 계속 돌았다.
  턴은 run-scoped 토큰으로 도구를 불렀고, 도구는 "어느 런인가"만 확인하고 "그 런을 아직 이 작업이
  맡고 있는가"는 확인하지 않았다.
- 옛 턴의 호출이 런의 샌드박스를 (런 id 로 이름 붙여) 다시 만들었고, 새 워커의 같은 이름 생성이 충돌했다.
- 나는 재claim 로그만 보고 성공이라 보고했다. 이어서 kill 실험을 하려고 봤더니 런은 이미 `failed` 였다.

## 핵심 통찰

1. **반납은 장부 상태만 바꾼다.** claim 을 OPEN 으로 돌리는 순간, 그 claim 아래에서 발급·위임한 모든 것
   (원격 턴, 서브프로세스, 토큰, 예약 콜백)은 "주인 없는 살아 있는 일"이 된다. 각각을 **끊거나**,
   최소한 **그 claim 에 묶어 거절되게** 해야 한다.
   - 끊기: 취소 경로에서 원격 세션에 kill 신호(shield + 짧은 타임아웃 — 이미 취소 중인 태스크 안이다).
   - 묶기(안전망): 위임 토큰에 claim id 를 넣고, 받는 쪽이 매 호출마다 "런이 RUNNING 이고 claimed_by 가
     이 값인가"를 확인. claim id 가 **프로세스마다 새로 생성**(uuid4)되는지 확인 — 머신 이름 같은 안정 id 면
     재시작 후에도 옛 토큰이 통과한다.
2. **"다시 가져갔다"와 "살아남았다"는 다른 사건이다.** 재시작 검증은 재claim 이후 **첫 몇 단계**(샌드박스
   생성, 첫 도구 호출)와 **런의 최종 상태**까지 봐야 한다. 그리고 로그는 **반납하는 쪽과 위임받은 쪽 둘 다**
   본다 — 이번 원인은 backend 로그에만 있었다.
3. **기대한 로그 이름이 안 찍히는 게 정상일 수 있다.** 작업 자신의 취소 경로가 먼저 반납하면 `stop()` 의
   정리 단계(`released_on_stop`)는 할 일이 없어 침묵한다. 체크리스트의 증거는 "어느 함수가 로그를 찍나"가
   아니라 **상태 전이**(running→open + 재claim)로 적는다.
4. **이런 경로는 저절로 거의 안 일어난다.** 배포가 실행 중 작업을 피해 미뤄지면, 재시작-중-실행은 운영에서
   몇 주씩 안 보인다. 일부러 재시작해서 재는 게 유일한 방법이다: 작업이 **원격 도구를 부르는 중**(받는 쪽
   로그에 호출이 찍힐 때)까지 기다린 뒤 graceful 한 번, `kill` 한 번.

## 체크리스트

- [ ] 반납 경로가 위임한 원격 일을 끊는가? 끊지 못하는 경우 받는 쪽이 claim 으로 거절하는가?
- [ ] claim id 가 프로세스마다 새것인가?
- [ ] 런 id 로 이름 붙인 자원(샌드박스·락·임시 디렉터리)을 두 프로세스가 만들 수 있는가? 충돌 시 재시도/정리가 있는가?
- [ ] 검증: 재claim 후 첫 자원 생성과 최종 상태까지 봤는가? 받는 쪽 로그도 봤는가?
