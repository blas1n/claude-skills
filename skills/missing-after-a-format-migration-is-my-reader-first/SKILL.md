# 포맷을 옮긴 뒤 사라진 항목은, 먼저 내 리더를 의심하라

## Problem
hpgg: 영웅 데이터 소스를 heroes-data(v4, 아카이브됨) → heroes-data2(HeroesDataParser v5)로 옮기며 `from_v5` 어댑터 작성. 재생성 diff 에서 바이킹의 기본 능력 5개(돌아야 이긴다! 등), 메디브·티리엘 id 가 사라짐.
- 1차 대응(틀림): "98304 데이터에 없다" → 이전 파일의 id 를 이어붙이는 carry-over + 경고 로그. 테스트까지 만들어 고정.
- 사용자 지적: "최신 데이터에만 빠진 걸 억지로 이은 거잖아 — 정말 빠진 건지, 게임에서 없어진 건지 확인해야".
- 확인해 보니: 2.57 특성이 여전히 그 능력을 강화(`LostVikingsMasterySpinToWin → LostVikingsSpinToWin`)하고, 2.57 문자열에도 이름이 있고, herodata 에 id 가 15번 등장 — **`heroUnits/HeroOlaf|Baleog|Erik/abilities`** 아래로 옮겨져 있었다. 메디브 PortalInstant 도 그대로 존재(라벨 그룹핑 변화로 키가 접두어로 넓어졌을 뿐), 티리엘 `TyraelA` 는 id 가 아니라 공통 접두어였는데 이름 조회 순서를 바꾼 내 변경 때문에 그룹이 깨진 것.
- 즉 사라진 3건 모두 **내 어댑터 결함**. carry-over 는 이를 숨겼다.

## Solution
1. 사라진 id 마다 새 원본 **전체**를 문자열 검색(`json.dumps(x).count(id)`) → 0이 아니면 경로를 찍어 본다(재귀 walk 로 path 출력).
2. 독립 증거 2~3개로 "게임/도메인에 아직 존재"를 판정: 그 id 를 참조하는 다른 레코드(특성 → 능력), 같은 버전의 문자열/로컬라이즈, 같은 파서의 이전 빌드.
3. 비교는 **소비자의 매칭 규칙**으로: 여기선 핫픽스 diff 가 접두어 최장 매칭이므로 "옛 id 가 새 키 중 하나로 여전히 매칭되는가"를 전수 검사(정확 일치 diff 는 접두어가 넓어진 걸 손실로 오판).
4. 라벨이 바뀐 항목은 소비자가 그 라벨에 실제로 도달하는지 확인(여기선 특성 매칭이 먼저라 도달 불가 → 무영향).
5. carry-over/fallback 은 위 검사로 "원본에 정말 없음 + 도메인에 아직 존재"가 확인된 경우에만, 이유를 적어서.

## Key Insights
- "새 소스에 없다"는 결론은 내 리더가 새 소스 전부를 읽었을 때만 성립한다. 포맷 개편은 거의 항상 **경로 이동**을 동반한다(하위 유닛, 중첩, 키 이름).
- 이어붙이기는 증상만 없애고 판별력을 없앤다 — 다음 빌드에서 진짜로 사라져도 모른다.
- 정확 일치 diff 와 소비자의 매칭 규칙(접두어·최장 일치)이 다르면, 정확 일치 diff 의 removed 는 손실이 아닐 수 있다.

## Red Flags
- 어댑터를 쓰자마자 removed 가 특정 엔티티(멀티 유닛 영웅·특수 케이스)에 몰려 있음
- "업스트림이 빠뜨렸다"는 결론을 원본 전체 검색 없이 내림
- 이전 산출물을 입력으로 다시 읽는 코드(자기 출력이 다음 입력이 되는 순환)
