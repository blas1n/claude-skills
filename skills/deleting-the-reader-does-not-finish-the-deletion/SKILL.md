# 삭제는 읽는 쪽만 지우면 안 끝난다

## Problem

- **증상**: 몇 주 전 "지웠다"고 기록된 키가 prod 데이터에 계속 나타난다. 코드를 grep 하면
  읽는 곳이 정말 0개다.
- **근본 원인**: 삭제 PR 은 **소비자**(읽는 코드)와 **하나의 기본값**만 건드리고 끝나기
  쉽다. 값을 **만드는** 경로는 보통 여럿이고 층도 다르다 — 다른 언어의 클라이언트,
  DDL `server_default`, 미러된 API 표면, 툴 설명을 읽는 에이전트.
- **흔한 오해**: "grep 해서 읽는 데가 없으니 끝" — grep 은 **독자 부재**를 증명하지
  **생산자 부재**를 증명하지 않는다. 자유형 JSON 칸은 쓰는 쪽이 읽는 쪽보다 오래 산다.

## Solution

1. **센서부터**: `WHERE <key> IS PRESENT AND created_at > <삭제 커밋 날짜>`.
   삭제 이후에 태어난 행이 하나라도 있으면 **생산자가 살아 있다** — 이게 혼자 증명한다.
2. **쓰기 경로를 전수로 세고 하나씩 지운다**(소거법). 감사 이벤트가 없으면 이게 유일한 길:
   - 각 클라이언트가 그 필드를 **보내는가** (보내는 것만 후보다)
   - 각 서버 스키마가 그 필드를 **거절하는가** (거절하면 후보에서 빠진다)
   - 남는 하나가 범인. 같은 행의 **다른 필드**가 후보를 더 좁혀 준다
     (예: "그 행은 `selection` 이 차 있는데 저 클라이언트는 `selection` 을 안 보낸다")
3. **층을 전부 세라.** 한 필드의 기본값이 사는 곳:
   앱 상수 · ORM `default` · DB `server_default` · 클라이언트 타입 · 스키마 문서 · 툴 설명.
   위층을 지워도 **아래 층이 대신 대답한다**.
4. **기존 데이터도 같이 벗겨라.** 읽는 코드가 0개임을 가드가 매 런 단언한다면 데이터
   정리는 동작상 no-op 이고, 안 하면 응답·로그·UI 가 계속 죽은 키를 실어 나른다.
5. 배포 후 **분모와 함께** 보고: `3/3 → 0/3`. 기준선은 **머지 전에** 떠라 — 배포된
   뒤엔 다시 못 뜬다.

## Key Insights

- **리터럴이 일치한다고 인과가 아니다.** prod 값이 DDL `server_default` 와 **글자까지
  똑같아서** 그게 범인이라고 거의 확신했는데, ORM 이 항상 컬럼을 명시해서 그 기본값은
  닿을 수조차 없었다. 진범은 다른 층이었다. 일치는 가설이지 증거가 아니다 —
  **그 경로가 실제로 실행되는지** 확인해라.
- **"어딘가가 아직 쓴다" 는 하나를 뜻하지 않는다.** 백로그에 한 줄로 적힌 잔재는
  대개 층이 여럿이다. 하나 고치고 닫지 마라.
- 삭제가 남긴 최악의 잔재는 데이터가 아니라 **반쯤 죽은 UI** 다 — 없는 값을 읽어
  틀린 상태를 보여 주고, 쓰면 서버가 거절한다. 그리고 **픽스처가 그 값을 넣어 주면
  테스트는 계속 초록**이다. 삭제 PR 의 체크리스트에 *"이 키를 넣어 주는 픽스처가 있나"*
  를 넣어라.
- 삭제 커밋의 **날짜**를 인수인계·이슈에 적어 둬라. 잔재를 잴 때 쓰는 유일한 경계선이다.
