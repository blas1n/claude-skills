# 같은 소스의 이웃이 다르게 보이면, 쿼리 단위를 diff 하라

## Problem
hpgg(Heroes Profile API 기반 HotS 통계)가 새 패치 2.57 이후에도 이전 패치를 보여줌. 사용자 질문: "수집이 안 된 거냐, 진짜 모자란 거냐".
- 1차 답(틀리진 않았지만 프레임이 좁음): 수집 정상, 현재 빌드 98304 가 HP 에 올라온 지 24h 라 SL 표본 30/91 < 절반 → 내일 자동 전환. **"패치 = 빌드 하나"라는 내 정의 안에서만** 답했다.
- 사용자가 같은 HP 를 쓰는 hotsgg.com 을 제시 → 페이지 RSC payload 에 `"Patch":"2.57.0","PatchType":"major"` — **빌드 두 개(98285 + 핫픽스 98304)를 합쳐서** 보고 있었다. 영웅당 판수 2.9배. 원인은 임계값(200판)이 아니라 **집계 단위**: 하루짜리 핫픽스가 표본을 0 부터 다시 시작시킨 것.
- 사용자 의도는 "핫픽스 포함, 정규 패치(x.y.z) 단위" — 예전에 기록된 결정("패치 = 빌드")이 의도와 어긋나 있었다.

## Solution
1. 이웃 서비스의 페이지를 받아(`curl -A Mozilla`) payload(Next.js RSC 등)에서 **레코드 하나**를 찾아 집계 키(버전·기간·타입 필드)를 읽는다. 렌더된 표가 아니라 원 데이터를 본다.
2. 내 쿼리 파라미터와 필드별로 diff → 단위 차이인지, 시점 차이인지, 공식 차이인지 분리. (같은 패치끼리 순위 상관 0.67 vs 다른 패치 0.52 처럼 수치로 기여도 확인)
3. 문서가 모호한 API 파라미터는 **일부러 틀린 값을 먼저** 보내본다: 에러(422)는 무과금이고 쿼터 헤더(`X-*-Quota-Remaining`)를 그대로 돌려준다 → 버킷별 잔여 쿼터를 공짜로 읽는다.
4. 유효 탐침은 1회만, 가장 쓸모 큰 조합으로. 결과를 이웃 수치와 대조해 의미를 검증(우리 789판 vs hotsgg 778판).

HP 고유 사실(프로젝트 HANDOFF 에도 기록):
- `timeframe_type=major` 는 **x.y**(`2.55` = 2.55.0~2.55.17 전부)이지 x.y.z 가 아니다. `major`+`2.57.0` → 422.
- 정규 패치 = `timeframe_type=minor&timeframe=<빌드1>,<빌드2>` 쉼표 나열 — HP 가 합산(heroes/stats, heroes/matchups 실측).
- 탐침 중 발견: 그 주 Heroes/Stats 잔여 12/70 — 일일 수집 8회로는 리셋 전에 바닥. 탐침 전에 잔여부터 읽었어야 했다.

## Key Insights
- "A 냐 B 냐" 질문에 내 정의 안에서 답하면 C(정의가 틀림)를 못 본다. 같은 소스의 이웃이 다르면 **정의가 다르다는 증거**다.
- 기록된 과거 결정("패치 = 빌드")도 사용자 의도와 대조 대상이다 — 문서에 있다고 의도인 건 아니다.
- 비싼 API 에서 실패 응답은 정보 채널이다: 허용값, 쿼터, 리셋 시각.

## Red Flags
- "임계값이 너무 빡빡한가?" — 먼저 단위/분모가 같은지 확인
- 경쟁 서비스가 같은 데이터로 더 많은 표본을 보여줌
- API 문서 예시가 한 형태뿐(`2.55`)인데 다른 형태(`2.57.0`)를 가정
- 주간 한도 API 를 잔여량 확인 없이 탐침
