# 초록은 배포를 증명하지 않는다 — 행을 재라

## Problem

- **증상**: 유닛 7,000건 통과 · CI 초록 · 배포 성공 · 헬스 200. 그런데 prod 에서
  기능이 **여전히 안 돈다.**
- **근본 원인**: 테스트 하네스가 프로덕션이 **주지 않는 것**을 보태고 있다.
  가장 흔한 셋:
  - **커밋**: 테스트가 `await session.commit()` 을 부른다. 프로덕션 디스패처는
    핸들러가 자기 커밋을 한 뒤 아무도 다시 커밋하지 않는다 → 행이 조용히 사라진다.
  - **PATH/런처**: 테스트는 내 셸에서 돈다. 프로덕션은 launchd/systemd 의
    최소 PATH 로 돈다 → `command not found` 가 프로덕션에서만 난다(반대도 난다).
  - **세션/컨텍스트**: 테스트가 워크스페이스 GUC·인증 컨텍스트를 세워 준다.

2026-09-23 실측: MCP 감사 배선을 고쳐 7,146건 통과 → 배포 → prod 에서 쓰기 1회 →
**감사 행 여전히 0건.** 세 번째 겹(커밋 부재)이 있었고, 유닛은 테스트가 커밋을
보태서 초록이었다.

## Solution

1. **고치기 전에 분모를 떠 둔다.** 배포 후엔 다시 못 뜬다.

```sql
SELECT count(*) FILTER (WHERE event_type LIKE 'x.%') AS mine, count(*) AS total FROM t;
-- 0 / 5571   ← 이 줄이 나중에 "1 / 5572" 를 의미 있게 만든다
```

2. **배포됐는지부터 확인한다** — 커밋 SHA 로. 태그가 아니라 실행 중인 것.

3. **프로덕션 경로로 한 번 시킨다.** 되돌릴 수 있는 no-op 이 가장 좋다
   (같은 값으로 update, 읽기 전용 프로브).

4. **행을 센다. 초록을 세지 마라.** 그리고 **음성 대조군**을 같은 창에서:
   읽기 툴은 행을 안 남기는가? 안 그러면 "전부 찍는" 구현과 구분이 안 된다.

5. 0이 나오면 **테스트가 무엇을 보태고 있는지** 찾아라. 그 줄을 지우고 테스트가
   빨개지는지 보라 — 빨개지면 그게 진짜 감지기다.

## Key Insights

- **테스트에서 그 줄을 지우는 것이 수정의 일부다.** 코드만 고치면 다음 리팩터가
  같은 구멍을 다시 낸다. 절단으로 확인: 고친 코드를 되돌렸을 때 **옛 테스트는
  초록이었고 새 테스트는 빨개진다.**
- **조용한 실패는 로그로도 안 잡힌다.** best-effort 경로(`try/except: pass`)는
  예외가 없으면 경고도 안 낸다 — `..._failed` 가 0건인 것이 "정상"의 증거가 아니다.
- **배포 후 실측이 자기 오류를 잡는 유일한 수단이다.** 이날 그 실측이 없었으면
  이슈는 "고쳤다"로 닫히고 감사는 계속 0건이었다.
